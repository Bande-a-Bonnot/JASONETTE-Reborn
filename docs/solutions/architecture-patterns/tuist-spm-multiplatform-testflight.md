# Tuist + SPM Multi-Platform Architecture for TestFlight Distribution

## Problem Summary

Building and distributing a single cross-platform SwiftUI app to TestFlight requires:
1. Platform-specific App bundle IDs, deployment targets, and signing
2. Per-platform assets and Info.plist configurations
3. Code sharing across platforms without duplication
4. Clean separation between configuration (Xcode/Tuist) and implementation (Swift Package)

Xcode project files are notoriously difficult to maintain in version control. Tuist solves this by generating .xcodeproj from declarative manifests, but Tuist does not bundle app code — it needs an external dependency (typically a Swift Package) containing the actual application entry point.

The key architectural challenge: **how do you link a Swift Package containing `@main` into Xcode app targets generated by Tuist?**

## Root Cause / Architectural Insight

### The Executable vs. Library Distinction

Traditional Swift Packages declare app code as `.executable` products:

```swift
// WRONG: SPM executables cannot be linked into Xcode targets
.product(name: "JasonetteApp", type: .executable, targets: ["JasonetteApp"])
```

SPM executables are standalone binaries for CLI tools. They **cannot** be linked into Xcode app targets — the linker expects to find the `@main` entry point inside the Xcode target itself.

**Solution: declare app code as `.library` products:**

```swift
// CORRECT: SPM libraries can be linked into Xcode targets
.library(name: "JasonetteApp-iOS", targets: ["JasonetteApp-iOS"]),
.library(name: "JasonetteApp-macOS", targets: ["JasonetteApp-macOS"]),
.library(name: "JasonetteApp-tvOS", targets: ["JasonetteApp-tvOS"]),
.library(name: "JasonetteApp-visionOS", targets: ["JasonetteApp-visionOS"]),
```

Each library target contains a single file with `@main`:

```swift
// Sources/JasonetteApp-iOS/App.swift
import SwiftUI
import Jasonette

@main
public struct JasonetteApp: App {
    public init() {}

    public var body: some Scene {
        WindowGroup {
            JasonetteNavigationView(url: ...)
        }
    }
}
```

Swift Package Manager allows multiple libraries with `@main` structs. The linker finds the entry point when a library is linked into an executable context (an Xcode app target).

### Tuist Shell Targets with External Dependencies

Tuist Project.swift defines sourceless shell app targets that are pure configuration:

```swift
.target(
    name: "Jasonette-iOS",
    destinations: [.iPhone, .iPad],
    product: .app,
    bundleId: "com.bande-a-bonnot.jasonette",
    deploymentTargets: .iOS("16.0"),
    infoPlist: .extendingDefault(with: [...]),
    sources: [],  // NO SOURCE CODE IN THIS TARGET
    resources: ["Resources/iOS/**"],
    dependencies: [.external(name: "JasonetteApp-iOS")],  // Link SPM library
    settings: .settings(base: SettingsDictionary()
        .automaticCodeSigning(devTeam: "TEAM_ID_HERE"))
),
```

Key properties:
- **`sources: []`** — This target contains no Swift source files. All code lives in the linked SPM library.
- **`resources: ["Resources/iOS/**"]`** — Platform-specific assets, icons, and resources bundled into the app.
- **`dependencies: [.external(name: "JasonetteApp-iOS")]`** — Links the SPM library containing the `@main` entry point.
- **`infoPlist: .extendingDefault(with: [...])`** — Per-platform Info.plist customizations (bundle display name, encryption declarations).
- **`settings: .settings(...)`** — Per-platform build settings (signing, deployment target).

When Xcode links this target with the SPM library, the linker discovers the `@main` struct and uses it as the app entry point. No explicit main file in the Xcode target is needed.

### Four-Platform Pattern

The architecture repeats identically for each platform:

| Platform | SPM Library | Tuist Target | Deployment Target | Bundle ID Suffix |
|----------|-------------|--------------|-------------------|------------------|
| iOS | `JasonetteApp-iOS` | `Jasonette-iOS` | iOS 16.0 | (none) |
| macOS | `JasonetteApp-macOS` | `Jasonette-macOS` | macOS 13.0 | `.macos` |
| tvOS | `JasonetteApp-tvOS` | `Jasonette-tvOS` | tvOS 16.0 | `.tvos` |
| visionOS | `JasonetteApp-visionOS` | `Jasonette-visionOS` | visionOS 1.0 | `.visionos` |

Each platform-specific library imports the shared `Jasonette` library (containing business logic, views, and models). Platform-specific entry points configure per-platform UI idioms if needed.

## Key Decisions Made

1. **Platform-specific libraries over a single executable.** One SPM library per platform enables conditional platform imports and UI idiom-specific configurations within each target's source files.

2. **Sourceless Tuist targets for configuration-only logic.** Tuist excels at expressing build configuration (signing, assets, deployment targets, Info.plist). Dedicating Tuist to that and delegating code to SPM creates a clean separation of concerns.

3. **Shared base `Jasonette` library for DRY code.** All platform libraries depend on the shared `Jasonette` library, which contains the `JasonetteNavigationView` and all platform-agnostic logic. Code duplication across platform entry points is minimal.

4. **External Tuist Package manifest.** The `Tuist/Package.swift` file declares SPM dependencies (the JasonetteApp package itself) to Tuist, allowing Tuist to resolve and link them without requiring the user to manually manage xcworkspace or .xcodeproj/project.pbxproj entries.

```swift
// Tuist/Package.swift
import PackageDescription

let package = Package(
    name: "Jasonette",
    dependencies: [
        .package(
            path: "."  // Points to ../Package.swift (the SPM root)
        )
    ]
)
```

5. **@main visibility requirement.** All `@main` structs in the platform libraries must be `public` so Tuist-generated app targets can link them. A `public init()` is also required.

6. **Multi-platform Swift version requirement.** Package.swift declares `platforms: [.iOS(.v16), .macOS(.v13), .tvOS(.v16), .visionOS(.v1)]` to ensure the compiler rejects incompatible platform deployments early.

## Distribution Workflow

After Tuist generates the Xcode project:

1. Replace `TEAM_ID_HERE` placeholder in Project.swift with your Apple Developer Team ID.
2. Run `tuist generate` to create the Xcode project.
3. Open `Jasonette.xcworkspace` in Xcode.
4. Select each target (Jasonette-iOS, Jasonette-macOS, etc.) and configure signing.
5. Archive and submit to TestFlight via Xcode's Organizer.

Tuist ensures the project structure is reproducible from manifests, preventing .xcodeproj drift.

## Prevention / Best Practices

1. **Verify `@main` visibility.** Ensure the entry point struct is `public` and has a `public init()`. Private entry points will fail at link time with cryptic "entry point not found" errors.

2. **Use `.external` dependencies in Tuist for SPM packages.** This tells Tuist to resolve the package externally (from a local path or git remote) and link it at the Tuist target level.

3. **Keep business logic in shared libraries.** Platform-specific libraries should be minimal — only the `@main` struct and platform-specific UI configuration logic. Move everything else to `Jasonette`.

4. **Commit Tuist manifests and generated .xcworkspace/.gitignore.** Tuist manifests (Project.swift, Tuist.swift, Tuist/Package.swift) are source of truth and should be versioned. Generated artifacts (the .xcodeproj, .xcworkspace) are typically gitignored.

5. **Test building each platform target early.** Before committing to this architecture, verify that `swift build` succeeds and that Xcode can open the Tuist-generated project without errors.

6. **Document team ID requirement.** Add a comment in Project.swift reminding developers to replace the placeholder before first use.

## Tradeoffs

### Advantages

- **Code reuse:** Shared `Jasonette` library; platform-specific glue in four small entry point files.
- **Declarative configuration:** All Xcode settings in Swift (Project.swift), not in .pbxproj files.
- **Reproducible builds:** Same manifests always generate the same Xcode project structure.
- **Easy maintenance:** Adding a new platform (e.g., Catalyst) requires only adding a new library target in Package.swift and a new Tuist target in Project.swift.
- **Per-platform signing/assets:** Each platform can have different bundle IDs, signing identities, and asset catalogs without complexity.

### Disadvantages

- **Tuist learning curve:** Developers unfamiliar with Tuist manifests may find them unfamiliar compared to Xcode's UI.
- **Manual team ID insertion:** The `TEAM_ID_HERE` placeholder must be replaced before signing works.
- **Extra build step:** `tuist generate` must run before Xcode can open the project.

## Related Concepts

- **Swift Package Manager (SPM)** — Provides `.library` vs `.executable` product types and cross-platform target composition.
- **Tuist** — Generates Xcode projects from declarative manifests; supports external SPM dependencies via `.external`.
- **@main attribute** — Swift 5.3+ entry point; the compiler looks for a single `@main` struct in the main executable or linked binary.
- **Multi-platform Swift development** — Using conditional compilation and platform-specific imports to adapt code across iOS, macOS, tvOS, visionOS.
