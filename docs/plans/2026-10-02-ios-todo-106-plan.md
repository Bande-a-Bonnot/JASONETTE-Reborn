## Diagnosis and confidence

The September 26 QA pass established that normal Home → Tutorial → Web
Container navigation reaches the animated index, and repeated taps on `svg`
leave that index visible. It did not establish whether a navigation callback or
network request occurred. Its host HTTP 200 checks do not prove simulator
networking. The initial planning stage performed source research only. The
root-owned behavioral failing baseline is recorded below.

The source establishes the following boundaries:

1. `Jasonpedia/webcontainer/index.json` renders each data item as an HTML
   component with an outer `href`. The SVG destination is an absolute HTTPS
   URL. The visible `svg` text lives inside a `div`, without a DOM anchor.
2. `ComponentView.body` wraps a component with `href` in a plain SwiftUI
   `Button`; it gives `href` priority over `action`. Its HTML dispatch builds an
   interactive `WKWebView`. Neither the HTML component nor its web view routes
   a web-content tap to the outer `href`. Embedded WebKit consuming the touch
   is the leading diagnosis, but this source structure alone does not prove
   which recognizer won the observed iOS touch.
3. `JasonetteView.sectionComponentView` supplies the `handleHref` callback and
   current document URL. `handleHref` resolves HTTP(S) references and emits a
   `.push` for this authored href. Existing tests cover those URL and request
   paths, but do not exercise the rendered HTML menu row or native tap delivery.
4. SVG content has a separate deterministic source incompatibility. `svg.json`
   includes `template2.json`; its resolved body template has the title `SVG
   Clock` and an object at `body.style.background` containing `type: html` and
   the SVG document. `JasonBody.style` decodes as `JasonStyle`, whose
   `background` is `String?`. Decoding that rendered template therefore fails
   at the background value. `JasonetteViewModel.render` falls back to a raw
   document without a body; after `$load` the view model can report template
   render failure. Even if decoding succeeded, `bodyBackgroundView` currently
   draws only color/image strings and would not display the clock HTML.
5. Existing `DocumentLoaderTests` exercise Web Container include expansion into
   an untyped template dictionary. They do not establish successful SVG body
   decoding or visual rendering.

The failure to leave the menu and the inability to render the SVG destination
are separate observations. Simulator acceptance must show both the in-app push
and actual clock content. A changed navigation title, a direct-entry launch, or
a host curl check alone cannot satisfy this todo.

## Minimal intended changes

### Outer activation owns an actionable HTML row

Give the HTML renderer an explicit interaction mode derived from the authored
component. For a component with outer `href`, let the existing SwiftUI button
receive taps over the embedded content. Apply the same rule to outer `action`,
which uses the identical existing button boundary; preserve `href` precedence.
For components with neither outer target, retain native HTML interaction.

Prefer a small hit-testing change over a JavaScript message bridge or another
tap recognizer. Pass the mode from the HTML registry case into `HTMLComponent`
and apply it at the actual embedded view boundary. If native WebKit interaction
is configured imperatively, update that setting before the existing
`loadedSource == source` early return so changing activation does not require
reloading identical HTML. Inline animation and content loading continue in
either mode. The focused regression must inspect the effective native
hit-testing behavior or hosted routing, in addition to the mode decision.

### Decode the legacy HTML body background in body context

Keep the component-wide `JasonStyle.background: String?` contract. Add a narrow
body decoding path that preserves an object-valued `style.background` as the
body background and removes only that object before decoding the remaining
`JasonStyle`. Use the existing `JasonBody.background: AnyCodable?` field as the
canonical rendered background, preserving an explicitly authored top-level
background when present. Preserve normal body style strings and unrelated
style properties. Do not use a blanket `try?` that silently drops malformed
styles. Verify encoding/decoding preserves the resulting background and other
body fields.

This can be implemented with `JasonBody` Codable support in the model file or
an extension file, whichever avoids interference with todo 107. There is no
need to change every component's background type or add a new `JasonStyle`
property. If a property is added during implementation, follow the repository's
Three-Place Rule and request the additional scope first.

### Render the SVG as a viewport background

Add an HTML-object branch to `JasonetteView.bodyBackgroundView`, extracting the
inline text, optional CSS, and optional URL using the existing HTML URL policy
and current document URL. Reuse `HTMLComponent` in a viewport sizing mode so
the web view fills the document background. Inline HTML rows retain their
existing measured content height. The viewport mode must avoid deriving its
own frame from HTML `scrollHeight`, which can create a height feedback loop for
`html, body { height: 100% }` backgrounds. Preserve color/image backgrounds and
the structural layering of sections, footer, and layers.

The SVG background is decorative and must allow app navigation and scrolling
to work. No general Web Container JavaScript action bridge is part of this
todo; the separate plain HTML interaction acceptance uses a component without
an outer activation target.
